# Plan — PE-014-reconciliation-poller

## Approach
A scheduled `app:reconcile-generations` command runs `ReconcileGenerationsAction` every minute on one server. It polls stale `queued` and `processing` rows through a new `retrieveGeneration()` on the Pixelforge contract, selected by a `last_provider_update_at` that only the transition action stamps, and applies each answer through that same action (D-06). It also re-dispatches PE-013's submit job, with the same ULID, for unsubmitted rows that were handed over or whose attempts stopped, and gives up on unconfirmed rows after 24 h. The polls stay inside D-44's budget and keep a reserve for submits, a cadence stored per row slows them with age, and a per-generation create lock keeps one create in flight.

## Story clarifications
- **PR size.** The story asks for a split into PE-014a and PE-014b. The project rule wins: one PR, with that split as the cut point after task 11.
- **Decision numbers.** New rows start at D-49. The story's give-up row is D-49. Task 21 records all of them, so the plan commit touches only `plan.md` and `story.md`.
- **Last provider update.** It is our clock when the transition action applied a snapshot, from a create response, a replay, a webhook or a poll. It is never Pixelforge's timestamps and never `updated_at`.
  - Ignored and refused snapshots write nothing.
  - A local failure and D-09's provider-cost-only write do not stamp it.
  - Rows from before the column get `updated_at` once, in the migration. That is their last transition, because submit bookkeeping never touches `updated_at` (D-45).
- **Staleness.** A row is stale when its last update is strictly older than the threshold: 2 min for `queued`, 3 min for `processing`.
- **Cadence (AC 6).** Each poll and re-dispatch first records `reconcile_recheck_at` = now + clamp(age ÷ 4, recheck, max recheck), where age is measured from `created_at`. With the defaults that is 1 min until 4 min of age, then growing to 15 min at 1 h. A 2 h row is therefore polled 4 times an hour.
  - It is written before the request, so a poll that throws still waits its turn.
  - A max below the minimum means the minimum.
- **Batch (AC 16).** At most `batch_size` rows a run, across polls and re-dispatches. Polls go first, oldest last provider update first. Re-dispatches and give-ups then take the rest, oldest created first. The stuck warning is a DB-only step with its own limit of `batch_size`.
- **Reserve (AC 17).** A poll is sent only while more than `submit_reserve` units remain in the current minute: 12 left gives 2 polls, then 10 left stops them. Re-dispatched jobs are not held to the reserve. They take a unit through PE-013's check when they run.
- **Failed polls (AC 1).**
  - A spent budget or a 429 stops the run's polls.
  - `not_found` is a warning with the generation and provider ids (AC 18).
  - Any other contract error is a warning with its `context()`.
  - None of them is retried inline: the row waits for its recheck.
  - An exception from the transition (or anything else) is caught per row and logged at error with the ULID, the provider id and the exception class, and the run goes on (AC 4).
- **What "an attempt" is (AC 13).** It is one run of the submit job, as PE-013 defines it: recorded before the budget and the request.
  - A re-dispatch is owed one run that the window does not stop. That run is owed while no attempt started at or after the re-dispatch instant (whole seconds, like the stored times).
  - After that run, PE-013's decision applies unchanged. If the outcome was not definitive and the row is latched, the stop hands it over, or leaves it handed over: back to the reconciler.
  - A row that was never latched and gets a "nothing created" answer past its window is failed free by its last outcome. That is PE-013's own rule, because no attempt was ever ambiguous.
  - A row never attempted (dispatch lost, worker died first) has its whole window ahead, so the re-dispatched job retries normally.
  - If the owed run finds the budget spent, it counts as the attempt. The row is handed back, and the next re-dispatch follows the cadence.
- **Re-dispatch (AC 12).** A `pending` row with no provider id is re-dispatched when it is handed over, or when its last attempt (else its creation) is strictly older than `redispatch_after`. It must also be due by `reconcile_recheck_at`. The same `SubmitGenerationJob` class is used, so its lock, budget, bookkeeping and window apply.
- **One create in flight (AC 15).** The lock covers the whole run, from the re-read to the recorded outcome. A run that waits on it records nothing, so it never touches the window, the latch or the owed run.
- **Give-up (AC 20).** It applies only to a `pending` row past `give_up_after` since creation, when the row next comes up in the unsubmitted step. That can be up to one recheck interval late (at most 15 min).
  - It goes through the transition action as a local failure, `lost`: free, with the hold released and one error log.
  - A give-up can race a re-dispatched create. The transition's row lock orders them. Either the row has advanced, so the local failure is refused and logged, or it is `lost` and a later success records provider cost only (D-09, the existing `recordProviderCostOnly` path).
- **Never give up a confirmed row (AC 21).** A row with a provider id only ever moves through Pixelforge's snapshots.
  - `reconcile_not_found_since` is the first `not_found` of the current streak. Any snapshot clears it, and other errors keep it.
  - Once the streak is past `give_up_after`, one error log names the ULID and the provider id, and `reconcile_not_found_reported_at` marks it as written.
  - The row keeps its hold and the stuck notice.
- **Stuck (AC 19).** It is any non-terminal row whose `created_at` is at or before now − `stuck_after`, on the server's clock.
  - History's `status_note` shows "Taking longer than usual — we're checking with Pixelforge" for it. That note wins over PE-013's retry note, which still shows on a younger `pending` row.
  - The notice needs no column. The reconciler logs one warning per such row, marked by `reconcile_stuck_warned_at`.
- **Copy.**
  - Stuck (`ReconcilePolicy::stuckNoteFor()`): "Taking longer than usual — we're checking with Pixelforge".
  - `lost` (`GenerationFailureCode`): "We couldn't confirm this generation with Pixelforge. You were not charged."
- **Bookkeeping.** The `reconcile_*` columns are written only by the reconciler's actions, through `recordReconcileBookkeeping()`: one UPDATE of those columns alone, never touching status, costs, the ledger or `updated_at`. Like D-45, they are not fillable.
- **The drop switch.** `[no-webhooks]` and the global switch are both decided at create, so turning the switch on affects only generations created afterwards. E2E never sets the switch.
- **Dev bounds.** Only the values the AC 22 spec needs are shortened in dev and E2E: the two thresholds, the recheck and the schedule. Re-dispatch, give-up and stuck keep production's values there, so other parallel specs never see a stuck note or a re-dispatch.
- **Logs.** They carry only generation and provider ids, statuses, outcomes, instants and `context()`, never a key, a secret, a body or a prompt.

## Decisions log (requirements §5)
| # | Decision | Why |
| --- | --- | --- |
| D-49 | Give up only on generations Pixelforge never confirmed (no provider id). After 24 h (`PIXELFORGE_GIVE_UP_AFTER`) they are failed `lost` and free through the transition action, and a late provider success records provider cost only (D-09). Generations with a provider id are polled until terminal and never failed locally; 24 h of `not_found` is logged once for the operator | It is a narrow exception to PE-013's "fail only when nothing was created", limited to `pending` rows, which the transition action already lets fail locally. It keeps History truthful and releases the hold. It never stops tracking a generation Pixelforge knows, so PE-016 and PE-018 provider costs stay complete. |
| D-50 | Staleness is judged by `last_provider_update_at`, our clock when the transition action applied a snapshot on any path. A row is polled once that is older than 2 min (`queued`) or 3 min (`processing`). The reconciler's cadence is a stored next check, `reconcile_recheck_at` = now + clamp(age ÷ 4, 1 min, 15 min). It is written before the request, in an UPDATE of the `reconcile_*` columns alone | The reconciler's own writes must never read as news from Pixelforge. A stored instant keeps the selection one indexed comparison and the formula in one PHP place. Writing it first means a poll that throws still waits its turn, so one bad row cannot drain the budget. Age ÷ 4 reaches 15 min at 1 h, so a 2 h row is polled 4 times an hour. |
| D-51 | A run handles at most 20 rows (`PIXELFORGE_RECONCILE_BATCH`). Polls go first, oldest last update first, and unsubmitted rows, oldest created first, take the rest. A poll is sent only while more than `PIXELFORGE_SUBMIT_RESERVE` (10) units of D-44's budget remain, read from the same key by `PixelforgeRequestBudget`. A spent budget or a 429 stops the run's polls; any other failure is logged and waits for the next check; an exception on one row is logged with its ULID and the run goes on | New submits keep priority: 12 left gives 2 polls. One class owns the key, the store and the limit, so the reserve can never read a different count. Polls are never retried inline, because the cadence is the retry. |
| D-52 | Re-dispatch reuses `SubmitGenerationJob` with the ULID and carries its re-dispatch instant. The job is owed one run that the window does not stop, while no attempt has started since that instant. After it, PE-013's decision is unchanged: a latched row is handed back, any other is failed free by its last outcome. A row is re-dispatched when handed over, or when its last attempt (else its creation) is older than 5 min (`PIXELFORGE_REDISPATCH_AFTER`), at D-50's cadence | The same key and bytes make Pixelforge replay a create that landed, with no second hold or charge, or create it now. Only the start-of-run window check is skipped, and only once, so the latch rule holds. An instant, not a flag, because a released job's payload never changes, and it lets duplicate re-dispatches collapse into one attempt. |
| D-53 | One create in flight per generation: `SubmitGenerationAction` holds `pixelforge-create:{ulid}` on the pinned database store for its whole run, for 90 s (the job's 60 s timeout + 30 s). A held lock releases the job for 5 s and records nothing. `WithoutOverlapping` and `ShouldBeUnique` are not used | The lock outlives a run killed at its timeout, so nothing can overlap it. `WithoutOverlapping` locks on the container's default cache store, which tests run as `array` and which the middleware cannot pin. `ShouldBeUnique` keeps its lock across `release()`, so a re-dispatch made while the first job waits would be dropped. It dedupes dispatches, not runs. |
| D-54 | `app:reconcile-generations` runs every minute with `withoutOverlapping(15 min)` and `onOneServer()` on the database cache (D-20). `PIXELFORGE_RECONCILE_EVERY` may name one of Laravel's sub-minute frequencies (5 s in dev and E2E); production sets nothing | Production's Hestia cron already runs `schedule:run` every minute on one server, so the droplet needs no change. 15 min is past the worst run (20 polls × 35 s). Sub-minute events repeat inside one `schedule:run` process, which memoizes its `onOneServer` mutex, so they still run on one server. |
| D-55 | The fake drops a generation's webhooks when its prompt holds `[no-webhooks]` (case-insensitive, anywhere), or, for manual testing, while `PIXELFORGE_FAKE_DROP_WEBHOOKS` is on. It is decided at create and stored as `drops_webhooks`; the lifecycle still advances and retrieve answers from it. E2E uses only the keyword | Playwright runs fully parallel on shared containers, so only a per-generation switch leaves the other specs their webhooks. Deciding at create matches D-35's chaos rolls. |
| D-56 | History says "Taking longer than usual — we're checking with Pixelforge" on any non-terminal generation 15 min (`PIXELFORGE_STUCK_AFTER`) after creation, by the server's clock, ahead of PE-013's retry note. The reconciler logs one warning per such row, marked by `reconcile_stuck_warned_at` | The notice needs no column, so it appears on time even if the reconciler is down. The marker keeps the log to one line per row. |

## Risks
- **Leaked cache rows.** Every test that polls or submits needs RefreshDatabase. The budget and the lock live in the pinned database store, so a test outside a transaction commits `cache` and `cache_locks` rows. `HttpPixelforgeClientTest` stays on the concrete driver.
- **The sync queue.** `QUEUE_CONNECTION=sync` would run a re-dispatched job inline. Re-dispatch tests fake `SubmitGenerationJob` (as `createGenerationFor()` does) and run it with `runSubmitJob()`.
- **Second precision.** Stored times are whole seconds, so the re-dispatch instant is whole seconds too, and tests travel in whole seconds.
- **Dev schedule.** The scheduler container reads its env at start: after task 11, `docker compose up -d`. `schedule:work` starts a fresh `schedule:run` each minute, so code changes apply within a minute. The worker still needs `make restart-worker`.
- **E2E time.** The AC 22 test takes about 15–30 s, and its derived timeout is about 72 s. If the single worker starves under parallel projects, raise `MARGIN` for this timeout only. Never add sleeps.
- **Short dev thresholds.** Other specs' rows are now also polled after 5 s. A poll can only report the fake's real state through the same transition, so it can advance a card earlier but never differently. Run the full `make e2e` in task 11.
- **The give-up race.** It is money-safe by the row lock and D-09 (Story clarifications). It is only logged, not prevented.
