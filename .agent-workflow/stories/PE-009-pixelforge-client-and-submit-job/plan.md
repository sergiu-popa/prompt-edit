# Plan — PE-009-pixelforge-client-and-submit-job

## Approach
`app/Support/Pixelforge` gains a `PixelforgeClient` contract with one operation, `createGeneration()`. Its HTTP driver sends an exact body built by `CreateGenerationPayloadData`, and it turns every answer into one of three things: a `CreatedGenerationData` (the PE-006 snapshot plus `replayed`), one typed error per documented code, or a single retryable ambiguous error. The create action queues a `SubmitGenerationJob` that carries only the ULID, and the queue releases it after commit. The job calls a Domain `SubmitGenerationAction`, which reloads the row, sends the create outside any transaction or row lock, and applies the answer through PE-006's `TransitionGenerationAction`. A `400`, `422` or `409` becomes a free local failure through that same action. Every other failure is rethrown, so the job retries with the same key and the same bytes.

## Data model
No migration. `local_failure_reason` is already a string, and `error_code`, `error_message` and `error_param` already exist. `error_param` is `varchar(255)`, which is why the parser bounds `param`.

## Decisions log (requirements §5)
Use the next free D-numbers after the highest one in `requirements.md` at commit time. PE-008 is done and its highest is D-30, so these are D-31, D-32 and D-33 unless a row lands first.

| # | Decision | Why |
| --- | --- | --- |
| D-next (error policy) | A Pixelforge error becomes a typed error only when its envelope is documented: a known `code` with that code's HTTP status, string `type`, `code` and `message`, no NUL byte in `code`, `message` or `param`, and a `param` of at most 255 characters. Everything else is one ambiguous error, retried with the same key: a transport failure or timeout, any other body, an undocumented code, a mismatched status, or a 2xx that is not a generation object. Only `400`, `422` and `409` fail a generation locally. | Fail locally only when Pixelforge definitely created nothing, because a replay is free. A create that timed out may have been accepted and billed, and failing it would lose the charge (D-09). Postgres text cuts at a NUL, so a stored reason is never silently truncated. |
| D-next (submission) | Submission is a queued job that carries only the ULID. The create action dispatches it, and the queue releases it only after commit (`ShouldQueueAfterCommit`). Each attempt re-reads the row, rebuilds the body from stored columns with one fixed JSON encoding, sends it outside any transaction or row lock, and applies the answer through the transition action. | A worker never reads an uncommitted row. Every retry sends byte-identical params, so Pixelforge replays the original instead of answering 409. A webhook that lands during the call is neither blocked nor undone (D-06). |
| D-next (timeouts, interim retries) | Timeouts nest: connect 5 s and request 30 s, below the job's 60 s, below the database queue's `retry_after` of 90 s, and a test pins the order. Redirects are never followed. Until PE-013, the job tries 5 times with backoff of 5, 15, 30 and 60 s. When it gives up, the generation stays non-terminal with its hold. | A hung request can never overlap its own retry. Following a redirect would re-send the key and the body somewhere we never configured. Stopping without failing keeps the invariant: PE-013 bounds retries by time, and PE-014 re-dispatches. |

## Tests
Feature tests use `RefreshDatabase` unless noted. Every test runs with stray HTTP prevented (`Tests\TestCase`). Driver and job tests use `InteractsWithPixelforgeApi`, which sets the sentinel key, so no real key is ever involved. Amounts are exact ints asserted with `assertSame`. "Unchanged" means `rawGenerationRow()` and `ledgerEntriesFor()` are equal before and after. The Lighthouse is `lighthouseRequest()`: hold −457,150,000, provider cost 305,510,000, charge 381,887,500.

## Risks
- **PR size is well over the ≈400-line budget.** The estimate is ≈2,300 changed lines, excluding `.agent-workflow`: ≈900 of production code and docs, and ≈1,400 of tests. The story's ~750 leaves out most of the tests. One PR per story is the rule even above the budget (`.agent-workflow/CLAUDE.md`), so this ships as one PR, and the PR description names the cut point.
  - The cut is after task 6.
    - PR A (tasks 1–6, ≈1,100) holds the contract, the driver, the DTOs, the typed errors and the config.
    - PR B (tasks 7–14, ≈1,200) holds the job, the dispatch, the rejections, the retries and the decisions.
  - PR A is safe on its own: nothing calls the client yet.
  - Tasks 7–8 add the job without dispatching it, so they are safe to ship apart from task 9.
- **The `sync` test queue runs the job inline after commit.** An exception from the job leaves the creator's call even though the row committed. That is why `createGenerationFor()` holds the job back. PE-011's controller tests must fake the job too, or a submit request would answer 500 in tests.
- **`Queue::fake()` ignores after-commit.** A faked job is recorded even inside a transaction that rolls back. AC 11's rollback test therefore uses the `database` queue, not the fake.
- **Local dev between PE-009 and PE-010.** The dev worker reads the real `PIXELFORGE_API_KEY` from `.env`, so a generation created locally would really be submitted. Nothing creates one until PE-011 (there is no UI, and the seeder makes none), and PE-010 switches local to the fake. Do not create generations in tinker meanwhile.
- **Interim behaviour (accepted by the story).** A 401, the daily cap, 429s, 503s and ambiguous outcomes retry 5 times, then stay non-terminal with their hold until PE-013 and PE-014. Each attempt also logs our warning plus the worker's report, which is noisy until PE-013 releases instead of rethrowing.
- **Strictness has a cost.** A definitive rejection with a malformed envelope, a NUL byte or a changed status is retried rather than failed. That is free, because nothing was created, but the hold stays until PE-013 and PE-014. This is the safe direction of the invariant.
- **A create answer without our `metadata.generation_id`** is refused by the transition, which logs the error, and the row stays pending. Pixelforge echoes metadata everywhere, so only an inconsistent Pixelforge causes this, and PE-014 recovers it.
- **Concurrent submits for one generation** are safe because they share the key: the second gets a replay, and the transition ignores it. PE-014 AC 15 adds the overlap guard.
- **Key in traces.** The key is never a method argument on the request path, and the constructor parameter is `#[SensitiveParameter]`, so a trace cannot show it even where `zend.exception_ignore_args` is off.
- **`app/Jobs/` is a new folder**, created by `make:job`. It follows the Laravel defaults the project already uses for `app/Console/Commands`.
- **Story status.** When this plan is committed, `story.md` moves to `planned`.
